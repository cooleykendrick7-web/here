Welcome flow + Daily Challenge (growth pack E): a fresh signup (users.onboarded=0) is redirected to /welcome instead of /home (login is untouched and always lands on /home; an onboarded user may revisit /welcome anytime to re-pick). Step 1 offers the 10 TOPICS as toggle chips (pick up to 5; POST /welcome/topics validates against TOPICS, dedupes, caps at 5, replaces user_topics, and seeds +4.0 'tag' affinity per saved topic). Step 2 lists follow suggestions (GET /welcome/suggestions.json): ranked by distinct hashtags on the author's posts from the last 30 days matching the viewer's saved topics (desc), then follower count (desc), then most recent post (newest first, authors with no posts last); self and blocked-either-way users are excluded; the Follow buttons hit the real POST /follow|unfollow endpoints. Step 3 shows the top 6 trending My Views (the _views_candidates set filtered to the last 14 days, scored 2×reactions + 3×comments, ties newest first). POST /welcome/done sets onboarded=1 and lands on /home; the page's skip link posts the same endpoint, so nobody is trapped. The Daily Challenge prompt comes from the module-level DAILY_PROMPTS bank (~21 prompts) picked as DAILY_PROMPTS[day.toordinal() % len] where day is the America/Chicago date (helpers CHICAGO_TZ / _today_chicago() / _today_str() / daily_prompt(); zoneinfo stdlib, with a manual US-DST fallback when tzdata is missing) — the same prompt for everyone all Chicago day. Answering posts to POST /posts with challenge=1 (+ next=/daily): create_post_from_form appends #HereDaily to the body when absent (so the hashtag hook stores 'heredaily') and stamps posts.challenge_date with today's Chicago date string. Streaks (current_streak): consecutive days in user_activity_days anchored at today, or at yesterday when today has no row yet (streak still alive); no anchor row = 0. Activity is recorded by record_activity() from exactly four hooks: visiting GET /home, creating any post (end of create_post_from_form), a reaction that leaves a reaction in place (POST /post/{id}/react when my_kind is not None — toggling OFF never counts), and adding a comment (POST /post/{id}/comment). GET /daily shows the huge prompt + date, the viewer's streak, a top-5 streak leaderboard (blocked-either-way users excluded, ties by name), the answer composer, today's visible answers (can_view_post + not-blocked + not-muted, newest first, rendered as post cards), and a "Yesterday: {prompt} — {count} answers" line. Home carries a dismissible 🔥 banner (localStorage 'here_daily_dismissed' = today's Chicago date string) and profiles show a "🔥 N day streak" chip when the owner's streak is >= 2. Nav gains "🔥 Daily" → /daily beside Invite in both the mobile menu and the sidebar.

Anonymous access: the anonymous surface is ONLY /, /login, /signup, /p, /l, /u, /join (plus static files and /sw.js) — everything else still requires login. QR note: the invite page loads a QR image from api.qrserver.com and that service receives ONLY the public invite URL (the qr_src built in GET /invite) — no user data beyond the shareable link itself.

Push notifications (Web Push): real phone notifications via the Push API + service worker + VAPID (RFC 8291/8292, pywebpush). `send_push(user_id, title, body, url, tag, ttl)` fires from exactly four moments — a new message (to the recipient, body = ~80-char preview, url /messages/{sender}, tag msg-{sender}), POST /calls/start (to the callee, "📞/📹 {name} is calling you…", ttl 60s; note: push delivery is best-effort and can lag the 45s ring — the in-app sheet stays the primary ring), a new call request (to the target), and a new friend request (to the target) — never to the actor. Sends run in a daemon thread and swallow all errors; 404/410 from the push service deletes the subscription row. All four moments are additionally gated by notifications_allowed(recipient, actor): a recipient who silenced the actor — or a pair blocked either way — gets no push (the in-app notification is gated by the same helper inside notify()). Platform truth (stated in the UI copy): iPhone push works ONLY inside the home-screen-installed web app (iOS 16.4+) — never in a Safari tab; Android Chrome works installed or in-browser; the native WebView wrappers (APK/IPA) do NOT support Web Push. Permission is requested ONLY from the "Turn on notifications" button (user gesture): Settings page "🔔 Notifications" card and the /app page, both via partials/push_panel.html, which also has Turn off and a "Send myself a test notification" (POST /push/test) control plus honest per-platform state messages. The SW's push/notificationclick handlers live in static/sw.js; its caching contract is unchanged (manifest + icons only, pages never cached).

Comment controls (Facebook-style): every comment and reply carries a ⋯ button (top-right of the bubble) shown only to viewers who may act on it — the comment's author sees "🗑 Delete comment"; the post's author, on someone else's comment, sees Delete AND "🚫 Block {name} from commenting on this post"; a viewer who is neither sees no button. The menu is ONE shared fixed sheet at body level in base.html (id cmenu-sheet — a menu inside a glass card would be trapped under the next card, same lesson as the aud sheets), and Delete asks for one inline confirm tap in the sheet. Replies: one level only — the Reply link under any comment opens an inline box; replying to a reply flattens onto the top-level comment and prefixes a linked "@Name" of the person replied to. Replies pass through the same moderation scan as comments, count toward the post's comment count (counts are computed from the comments table), and inherit the post's visibility — there is no separate reply privacy. Per-post comment blocks (post_comment_blocks) gate NEW comments and replies on that one post for that one user; the blocked user sees the blocked note instead of the comment box; the author manages the list from the post card's "🚫 Blocked (N)" sheet.

Message delete-for-me (Facebook-style "delete conversation"): users can delete a single message or a whole conversation FROM THEIR OWN VIEW ONLY — the other participant's copy is untouched and rows are NEVER removed from `messages` (owner moderation/flags keep working on the raw rows; only owner tooling ever hard-deletes). Mechanics: POST /messages/{mid}/delete records message_hidden(mid, caller) (participant-only; non-participants get a plain "Message not found." redirect so ids can't be probed); POST /messages/{fid}/delete-thread upserts thread_deletes(caller, fid, hidden_before=now). Every user-facing message query (inbox thread list + previews, Sent tab, thread view, inbox unread counts AND the global nav unread_msgs badge) applies BOTH filters for the current viewer via `_vis_frag()` in app.py: drop rows in message_hidden for the viewer, and drop rows with created_at <= the viewer's watermark for that conversation. Consequences: a conversation with no visible rows vanishes from that viewer's inbox (preview/timestamp always come from the latest VISIBLE message); the thread page renders empty with a working composer; a NEW message after the watermark revives the thread showing only post-watermark messages, and it notifies/pushes normally. Call system notes are ordinary message rows and follow exactly the same rules. UI: a ⋯ button (.mmenu-btn) on every inbox/Sent conversation row (outside the row link), in the thread header, and on every message's time line opens ONE shared body-level sheet (#dmenu-sheet in base.html, same fixed-sheet pattern as the comment menu) with an inline confirm step whose wording states the for-me nature ("It only leaves YOUR inbox — they keep their copy…"). Notification hygiene — taps self-clear + clear-all: a tap notification points at the tapper's profile (link = /user/{tapper_id}), and it deletes ITSELF once it has been seen or answered: GET /user/{id} deletes the viewer's notifications with kind='tap' AND link='/user/{id}' (only taps, only that person), and POST /tap/{id} does the same for the tapper after recording the tap-back. People search still finds private users, with a 🔒 marker (users dict carries is_private). Call multitasking (client-side only, base.html — no endpoint changes): an active call can be MINIMIZED (⌄ button or downward swipe on the overlay) into a floating tile (#call-mini, z-index 1500 — above page content, below the body-level sheets); minimizing MOVES the live #call-remote-video element into the tile via appendChild (same node, srcObject untouched, stream never restarts) and restoring moves it back to its overlay slot. Go Live (WebRTC, DB-signaled — same architecture as 1:1 calls; media is phone-to-phone, nothing recorded or relayed): a floating "🔴 Go Live" tab in base.html (logged-in users, z-index 900 — below the call mini tile 1500 / sheets 2000 / story viewer 2500 / call overlay 3100; NOT rendered on /live/ pages, which pass hide_golive) opens a title sheet -> POST /live/start -> the watch page. TOPOLOGY (panel mesh): every PANELIST sends to every watcher (one send-peer per watcher, the panelist always offers) and panelists are two-way with each other — for a panelist pair, whoever sits EARLIER in panel_order offers; a watcher joins by POSTing a 'hello' signal to the host, panelists learn the room roster from the state poll's panel/viewer_list and open/prune peers off it. Watchers are receive-only. Fixed offerer per pair = no negotiation glare, matching the calls caller-offers pattern; the ICE config literal is duplicated in live.html (keep in sync with base.html). Polls: signals ~2s, state ~3s, heartbeat ~10s. The host's beforeunload beacons POST /live/{id}/end; watchers/panelists beacon /leave. Stale sweep: host_seen_at older than 90s auto-ends the room on any live read/write; ending settles join requests/invites (pending->declined, approved->left), marks every member left, and revokes every admin appointment. END-LIVE NAVIGATION (host only): when the room ends — whether the host tapped End Live or the state poll first reports 'ended' (owner kill switch, stale sweep) — the HOST's live page navigates straight to their own profile ('/user/' + host id, one-shot inside teardownEnded); watchers/guests keep the ended face. DISCOVERY: home gets a "🔴 Live now" strip (live_now_for(viewer) — only rooms the viewer may watch) above the composer; the /lives discovery page (GET /lives, lives.html) lists the same rooms as cards ordered friends first, then followed hosts, then everyone else (within each group: watchers/viewers DESC, then newest/created_at DESC) — live_now_for rows carry panel_count + created_at, _lives_page_list annotates following — and the page polls GET /lives.json (~30s) to re-render; profiles also carry a "🔴 Lives" action link to /lives on every profile; profiles show a pulsing "🔴 LIVE — watch now" button when the profile owner is live (profile.live_id; suppressed on the locked private face — non-friends don't even learn they're live); notifications kinds 'live' (host went live) and 'live_invite' (invited to a panel). PERMISSIONS: _live_can_watch(viewer, live, owner_on) is the single gate for the page, state, comments, signals, join, like — host always, owner context always (same bypass as private profiles/blocks), blocked-either-way never, a viewer with a live_bans row for THIS room never, private-profile host = friends only; a refused page renders the same face as an ended live so nothing about the room leaks. ROLE MATRIX (helpers: _live_role -> 'host'|'admin'|'member'|'watcher', _live_is_admin, _live_panel_ids; a user can be member AND admin — admin is the reported role, host trumps): HOST — end the live, appoint/remove admins, invite, decide join requests, kick anyone but themselves, mute any member, reorder tiles, delete ANY live comment. My Views ranking (GET /views.json is the feed brain; templates/views.html is a dumb renderer over it): CANDIDATES are posts carrying an UPLOADED video file — posts.media's extension is in VID_EXTS {mp4, mov, webm}. The post's kind is NOT the test: a text post with a video file attached counts; a kind='video' post whose video is a YouTube/Vimeo link (video_url set, no file) does NOT — link videos stay on the wall. Share rows never count (their media lives on the original). On top of the media test: the viewer must pass can_view_post (the ONLY privacy gate — friends-only videos are friends-only here too, private-profile authors are friends-only, per-post hide-from applies), the author must not be blocked either way with the viewer, must not be muted by the viewer, and the viewer must not hold a 'hidden' view_event for the post. SCORE per candidate (weights are named VIEWS_* constants in app.py; the payload includes the final score): +30 if the author is the viewer's friend; +25 if the viewer follows the author; + the viewer's learned AUTHOR affinity for that author, clamped to ±40; + the viewer's learned TAG affinity summed over the post's hashtags, each clamped to ±30 and the total tag contribution clamped to ±45; + popularity = min(20, 2×reaction count + 3×comment count); + recency = max(0, 20 − age in days) (fractional — a just-posted video gets ~+20); −35 if the viewer already has a 'seen' event for the post (a demotion, never an exclusion: repeats sink but can still fill the tail). ORDER: score DESC, then created_at DESC. LEARNING (user_affinity rows; your own posts never teach you author affinity): first 'seen' (POST /views/{id}/seen, fired by the client when a video starts playing) → the post's hashtags +0.5, its author +0.5. First 'completed' (>=85% watched) → +1/+1. Reactions and comments made from the feed UI go through the wall's own endpoints (POST /post/{id}/react, POST /post/{id}/comment — unforked); the client then reports the act to POST /views/{id}/engage ({kind:'react'} → +2/+2, {kind:'comment'} → +3/+3). The server trusts the client's engage report exactly like it trusts 'seen' — the deltas are small, self-scoped (they only tune the reporter's own feed), and the alternative (threading teach-hooks through the wall endpoints) would fork rules the feed must not own. INTEREST (POST /views/{id}/interest): the explicit teacher, also behind the feed's ⋯ menu and the periodic "Are you interested in more like this?" prompt card the client inserts after the 3rd watched view of a session and then every 8 more (the card names the last watched video's first hashtag, or its author when it has none): interested=true → hashtags +10, author +10; interested=false → −10/−10 AND a 'hidden' view_event for that post. The feed UI: full-screen snap cells (video loops, autoplays muted at >=50% visibility via IntersectionObserver, pauses off-screen, tap toggles play/pause, a session-level 🔊 unmutes), right rail (author avatar + follow toggle through POST /follow|unfollow, ❤️ = the 'love' reaction through POST /post/{id}/react with count + my_reaction state, 💬 opens the comments sheet fed by GET /views/{id}/comments with posting via POST /post/{id}/comment, ⋯ = the interest menu), caption hashtags render as chips that apply the ?tag= filter, and the "➕ Post a View" composer is a plain multipart form to POST /posts with kind='video' + next='/views'.

## YouTube music (stories + post wall)

Music on HERE is YouTube-only: songs stream through YouTube's official
embedded (IFrame) player — the artist's own upload under YouTube's
licenses. There is NO preset catalog and NO MP3-upload path anymore
(the Kevin MacLeod preset pack and the My Music upload were removed at
the owner's order; the music_tracks / story_music_uploads tables remain
as unused legacy). Spotify/Apple are never integrated (their terms
forbid this use) and audio is never scraped or self-hosted.

Attach flow (identical for the story composer and the wall composer):
the user pastes a YouTube link (or taps a "🔥 Popular on HERE" row),
the client asks POST /music/preview, the server extracts the video id
with youtube_id_from() (bare id, watch, youtu.be, music.youtube.com,
shorts, embed, live, m. — candidate must match ^[A-Za-z0-9_-]{11}$)
and gates on youtube_oembed() (stdlib urllib, ~5s timeout; 401/404 =
not embeddable). At save time _resolve_music() re-validates: a pasted
link re-runs oEmbed; an id-only Popular pick re-checks the id shape
and copies the title/artist/thumb snapshot from an existing attachment
of the same video. A song that can't be embedded FAILS the save (no
story/post is created) with the flash "That video can't be played
inside HERE — try a different upload of the song." Only the validated
11-char id + snapshot are ever stored, so no arbitrary URL can become
an iframe src. Shared client wiring (hereLoadYT / hereMusicPicker)
lives in base.html; the picker markup pattern (.music-picker with
.mp-* hooks) is the same in story_new.html and home.html.

Playback:
- Story viewer: for kind='youtube' a VISIBLE mini player (200x113,
  bottom-left, above the viewers bar, with a 🎵 title — artist label)
  loads the id, seeks to music_start, sets music_volume, and plays;
  a 250ms tick loops the segment under long video stories and pauses
  it at the segment end otherwise; hold-to-pause pauses it; advancing
  or closing destroys it. Photo-story display time stays the clip
  length clamped to 5–30s. If audible autoplay is blocked, the 🔊
  tap-for-sound chip appears and tapping plays + sets the volume.
- Post wall: post_card.html renders a music bar (64px thumbnail,
  🎵 title — artist, ▶/⏸). The first tap lazily creates the player in
  a visible 16:9 area in the card (height capped at 200px) and plays
  from music_start; only one post plays at a time (starting another
  destroys the previous player). Unplayed posts load no iframes.
  A bare YouTube link pasted in post TEXT still auto-embeds as before
  — that behavior is separate and unchanged.
- User audio POSTS (kind='audio' MP3 uploads) are a post type and are
  untouched by all of the above.

- live_game_plays(game_id, user_id, value INTEGER, best INTEGER, plays INTEGER DEFAULT 0, PRIMARY KEY(game_id, user_id)) — one row per player per game. guess: value = the player's current guess (best unused). dice: value = last roll, best = highest roll so far, plays = roll count.
- game_matches(id, kind TEXT 'ttt'|'rps', a_id, b_id, state TEXT (JSON), turn_id NULL, winner_id NULL, is_draw INTEGER DEFAULT 0, status TEXT 'active'|'done' DEFAULT 'active', created_at, updated_at) — an asynchronous 1-v-1 friend challenge. ttt state = {"board": [null ×9]}; a_id is X and moves first; turn_id = whose move it is (NULL when done). rps state = {a_pick, b_pick, round, a_wins, b_wins, last} — picks are null while a round is open; `last` = the most recently resolved round {a_pick, b_pick, winner_id (null = tie), round}.

Live room games: the host or a live admin (the same _live_poll_mod_gate as polls) can POST /live/{id}/game/start (JSON {kind: 'guess'|'dice'}; anything else → 400) — starting auto-ends the room's active game (only ONE active game per live), and 'guess' deals a fresh secret server-side. POST /live/{id}/game/play requires the player to be IN the room (the same _live_access gate as poll voting): for guess, {guess} must be an integer 1–100 (else 400) and sets/replaces the player's guess; for dice the body is ignored and the server rolls 1–6, updating value/best/plays (the response also carries the fresh `roll`). With no active game, play answers 409. POST /live/{id}/game/end (host/admin) settles the game: guess winners = smallest |guess − secret|, all ties win; dice winners = highest best, ties share; no plays → no winners. Ending a live ends its active game too (_end_live_row, mirroring polls). The live state payload (GET /live/{id}/state) gains active_game {id, kind, players: [{name, display}], my_play} — guess display = the player's guess number (public once made), dice display = "🎲 best {best} ({plays} rolls)", my_play = my guess or my best — and last_game {id, kind, summary, winners: [names]} (+ secret for guess only), which rides along ONLY while no game is active, mirroring last_closed_poll. Friend challenges: POST /games/challenge (login, JSON or form {kind, user_id}) — the target must be an accepted friend (is_friend, else 403) and not the challenger (400); it creates the match (ttt: empty board, a_id = challenger is X and moves first; rps: fresh round state) and notify()s the target ("🎮 {name} challenged you to {game}!") linking /games/match/{id}. GET /games/match/{id} (login; participants only — anyone else, including for unknown ids, gets 404) renders game_match.html per kind: ttt = a 3×3 grid, cells tappable only on my turn, marks from state, a result banner when done; rps = three big buttons (🪨 📄 ✂️) while I haven't picked this round, "You picked — waiting on {name}…" after I pick, and the round result + score once a round resolves. An opponent's rps pick is NEVER rendered (page or JSON) while a round is open — only whether they have picked; resolved rounds are public history via state.last. POST /games/match/{id}/move (participants only, else 404; a finished match → 409): ttt {cell 0–8} validates my turn (403) and an empty cell (400), places my mark (X = a_id, O = b_id), wins on any of the 8 lines, a full board is a draw; rps {choice 'rock'|'paper'|'scissors'} stores my pick hidden (re-picking → 400) and, once both picks are in, resolves the round (rock>scissors>paper>rock; a tie round scores nobody), bumps the winner's wins, clears the picks, advances round, and ends the match when someone reaches 2 round-wins. The opponent is notify()d on every move / round resolution ("🎮 Your move in {game} vs {name}", or the result text on the deciding move), and moves call record_activity (they count toward streaks). POST /games/match/{id}/rematch (participant; match must be done, else 409) creates a NEW match of the same kind between the same players, swapping who starts (ttt: the previous b_id becomes a_id/X and moves first; rps keeps a/b), notify()s the other player, and redirects to the new match. POST /games/match/{id}/forfeit (participant; active match only, else 409) ends the match with the other player as winner and notify()s them.

## Live WebRTC: ICE config, membership truth, diagnostics (2026-10-23 fix)

ICE (single source): GET /ice.json (public — the values are the same community credentials already shipped in the templates) returns {"iceServers": [...]} from get_ice_servers() in app.py: the HERE_ICE_SERVERS env var (a JSON array of RTCIceServer dicts) when set AND valid (non-empty list of dicts each with a `urls`), else DEFAULT_ICE_SERVERS (Google STUN + Open Relay TURN). WARNING: the Open Relay TURN is a free community relay with a data cap — fine for launch, not a guaranteed relay; swap in private TURN credentials via HERE_ICE_SERVERS, no code change needed. Both WebRTC clients (templates/live.html mesh, templates/base.html 1:1 calls) call getIceConfig() once (cached promise): fetch /ice.json raced against a 1.5s timeout, replace their ICE_CONFIG with the result, and keep the hardcoded literal in each file as the fallback when the fetch fails/times out — peer creation never blocks on the fetch.

Panel membership truth: GET /live/{id}/state's my_panel.am_member is TRUE for the host (the host is panelist #1 by role and is never a live_members row; membership = is_host OR an active member row). A False here once demoted the host's own client to watcher on its first poll — tearing down every peer and ignoring every hello — which was the root cause of Ken's "can't see or hear anyone either way" live report. The live.html client additionally treats is_host as membership in syncMembership so a payload can never demote the host again.

Live negotiation (client, templates/live.html): the fixed offer rule is unchanged (panelist→watcher: panelist offers; panelist↔panelist: earlier panel position offers, later one hellos). All SDP work per peer is serialized on a per-peer promise chain (makeOffer + offer/answer handling) so setRemoteDescription calls can't interleave. A hello arriving while the pc is not 'stable' is recorded as pendingHello and acted on at 'stable' (signalingstatechange), never dropped; a non-offerer whose first hello predates its local media re-hellos once media is ready. Automatic ICE restart is bounded to ONCE per peer per failure episode (counter resets on 'connected'). Remote <video> tiles are created muted + playsInline (iOS autoplay); sound starts OFF for everyone and the 🔊 toggle (shown to panel members as well as watchers) unmutes.

Diagnostics (client): window.__liveDiag = {peers: {uid: {state, iceState, signalingState, hasRemoteTrack, hasLocalSenders, restarts}}}, refreshed on every peer event + a 1s interval. Each remote tile's label row carries a .live-conn-dot: grey = connecting/new, green = connected, red = failed or disconnected past a 5s grace; tapping a RED dot retries that peer (ICE restart + re-offer for the offerer, close + re-hello for the answerer).
