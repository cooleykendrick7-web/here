Welcome flow + Daily Challenge (growth pack E): a fresh signup (users.onboarded=0) is redirected to /welcome instead of /home (login is untouched and always lands on /home; an onboarded user may revisit /welcome anytime to re-pick). Step 1 offers the 10 TOPICS as toggle chips (pick up to 5; POST /welcome/topics validates against TOPICS, dedupes, caps at 5, replaces user_topics, and seeds +4.0 'tag' affinity per saved topic). Step 2 lists follow suggestions (GET /welcome/suggestions.json): ranked by distinct hashtags on the author's posts from the last 30 days matching the viewer's saved topics (desc), then follower count (desc), then most recent post (newest first, authors with no posts last); self and blocked-either-way users are excluded; the Follow buttons hit the real POST /follow|unfollow endpoints. Step 3 shows the top 6 trending My Views (the _views_candidates set filtered to the last 14 days, scored 2×reactions + 3×comments, ties newest first). POST /welcome/done sets onboarded=1 and lands on /home; the page's skip link posts the same endpoint, so nobody is trapped. The Daily Challenge prompt comes from the module-level DAILY_PROMPTS bank (~21 prompts) picked as DAILY_PROMPTS[day.toordinal() % len] where day is the America/Chicago date (helpers CHICAGO_TZ / _today_chicago() / _today_str() / daily_prompt(); zoneinfo stdlib, with a manual US-DST fallback when tzdata is missing) — the same prompt for everyone all Chicago day. Answering posts to POST /posts with challenge=1 (+ next=/daily): create_post_from_form appends #HereDaily to the body when absent (so the hashtag hook stores 'heredaily') and stamps posts.challenge_date with today's Chicago date string. Streaks (current_streak): consecutive days in user_activity_days anchored at today, or at yesterday when today has no row yet (streak still alive); no anchor row = 0. Activity is recorded by record_activity() from exactly four hooks: visiting GET /home, creating any post (end of create_post_from_form), a reaction that leaves a reaction in place (POST /post/{id}/react when my_kind is not None — toggling OFF never counts), and adding a comment (POST /post/{id}/comment). GET /daily shows the huge prompt + date, the viewer's streak, a top-5 streak leaderboard (blocked-either-way users excluded, ties by name), the answer composer, today's visible answers (can_view_post + not-blocked + not-muted, newest first, rendered as post cards), and a "Yesterday: {prompt} — {count} answers" line. Home carries a dismissible 🔥 banner (localStorage 'here_daily_dismissed' = today's Chicago date string) and profiles show a "🔥 N day streak" chip when the owner's streak is >= 2. Nav gains "🔥 Daily" → /daily beside Invite in both the mobile menu and the sidebar.

Push notifications (Web Push): real phone notifications via the Push API + service worker + VAPID (RFC 8291/8292, pywebpush). `send_push(user_id, title, body, url, tag, ttl)` fires from exactly four moments — a new message (to the recipient, body = ~80-char preview, url /messages/{sender}, tag msg-{sender}), POST /calls/start (to the callee, "📞/📹 {name} is calling you…", ttl 60s; note: push delivery is best-effort and can lag the 45s ring — the in-app sheet stays the primary ring), a new call request (to the target), and a new friend request (to the target) — never to the actor. Sends run in a daemon thread and swallow all errors; 404/410 from the push service deletes the subscription row. All four moments are additionally gated by notifications_allowed(recipient, actor): a recipient who silenced the actor — or a pair blocked either way — gets no push (the in-app notification is gated by the same helper inside notify()). Platform truth (stated in the UI copy): iPhone push works ONLY inside the home-screen-installed web app (iOS 16.4+) — never in a Safari tab; Android Chrome works installed or in-browser; the native WebView wrappers (APK/IPA) do NOT support Web Push. Permission is requested ONLY from the "Turn on notifications" button (user gesture): Settings page "🔔 Notifications" card and the /app page, both via partials/push_panel.html, which also has Turn off and a "Send myself a test notification" (POST /push/test) control plus honest per-platform state messages. The post's kind is NOT the test: a text post with a video file attached counts; a kind='video' post whose video is a YouTube/Vimeo link (video_url set, no file) does NOT — link videos stay on the wall. Share rows never count (their media lives on the original). On top of the media test: the viewer must pass can_view_post (the ONLY privacy gate — friends-only videos are friends-only here too, private-profile authors are friends-only, per-post hide-from applies), the author must not be blocked either way with the viewer, must not be muted by the viewer, and the viewer must not hold a 'hidden' view_event for the post. SCORE per candidate (weights are named VIEWS_* constants in app.py; the payload includes the final score): +30 if the author is the viewer's friend; +25 if the viewer follows the author; + the viewer's learned AUTHOR affinity for that author, clamped to ±40; + the viewer's learned TAG affinity summed over the post's hashtags, each clamped to ±30 and the total tag contribution clamped to ±45; + popularity = min(20, 2×reaction count + 3×comment count); + recency = max(0, 20 − age in days) (fractional — a just-posted video gets ~+20); −35 if the viewer already has a 'seen' event for the post (a demotion, never an exclusion: repeats sink but can still fill the tail). ORDER: score DESC, then created_at DESC. LEARNING (user_affinity rows; your own posts never teach you author affinity): first 'seen' (POST /views/{id}/seen, fired by the client when a video starts playing) → the post's hashtags +0.5, its author +0.5. First 'completed' (>=85% watched) → +1/+1. Reactions and comments made from the feed UI go through the wall's own endpoints (POST /post/{id}/react, POST /post/{id}/comment — unforked); the client then reports the act to POST /views/{id}/engage ({kind:'react'} → +2/+2, {kind:'comment'} → +3/+3). The server trusts the client's engage report exactly like it trusts 'seen' — the deltas are small, self-scoped (they only tune the reporter's own feed), and the alternative (threading teach-hooks through the wall endpoints) would fork rules the feed must not own. INTEREST (POST /views/{id}/interest): the explicit teacher, also behind the feed's ⋯ menu and the periodic "Are you interested in more like this?" prompt card the client inserts after the 3rd watched view of a session and then every 8 more (the card names the last watched video's first hashtag, or its author when it has none): interested=true → hashtags +10, author +10; interested=false → −10/−10 AND a 'hidden' view_event for that post. The feed UI: full-screen snap cells (video loops, autoplays muted at >=50% visibility via IntersectionObserver, pauses off-screen, tap toggles play/pause, a session-level 🔊 unmutes), right rail (author avatar + follow toggle through POST /follow|unfollow, ❤️ = the 'love' reaction through POST /post/{id}/react with count + my_reaction state, 💬 opens the comments sheet fed by GET /views/{id}/comments with posting via POST /post/{id}/comment, ⋯ = the interest menu), caption hashtags render as chips that apply the ?tag= filter, and the "➕ Post a View" composer is a plain multipart form to POST /posts with kind='video' + next='/views'.

## YouTube music (stories + post wall)

Music on HERE is YouTube-only: songs stream through YouTube's official
embedded (IFrame) player — the artist's own upload under YouTube's
licenses. There is NO preset catalog and NO MP3-upload path anymore
(the Kevin MacLeod preset pack and the My Music upload were removed at
the owner's order; the music_tracks / story_music_uploads tables remain
as unused legacy). Spotify/Apple are never integrated (their terms
forbid this use) and audio is never scraped or self-hosted.

Attach flow (identical for the story composer and the wall composer):
the user pastes a YouTube link (or taps a "🔥 Popular on HERE" row),
the client asks POST /music/preview, the server extracts the video id
with youtube_id_from() (bare id, watch, youtu.be, music.youtube.com,
shorts, embed, live, m. — candidate must match ^[A-Za-z0-9_-]{11}$)
and gates on youtube_oembed() (stdlib urllib, ~5s timeout; 401/404 =
not embeddable). At save time _resolve_music() re-validates: a pasted
link re-runs oEmbed; an id-only Popular pick re-checks the id shape
and copies the title/artist/thumb snapshot from an existing attachment
of the same video. A song that can't be embedded FAILS the save (no
story/post is created) with the flash "That video can't be played
inside HERE — try a different upload of the song." Only the validated
11-char id + snapshot are ever stored, so no arbitrary URL can become
an iframe src. Shared client wiring (hereLoadYT / hereMusicPicker)
lives in base.html; the picker markup pattern (.music-picker with
.mp-* hooks) is the same in story_new.html and home.html.

Playback:
- Story viewer: for kind='youtube' a VISIBLE mini player (200x113,
  bottom-left, above the viewers bar, with a 🎵 title — artist label)
  loads the id, seeks to music_start, sets music_volume, and plays;
  a 250ms tick loops the segment under long video stories and pauses
  it at the segment end otherwise; hold-to-pause pauses it; advancing
  or closing destroys it. Photo-story display time stays the clip
  length clamped to 5–30s. If audible autoplay is blocked, the 🔊
  tap-for-sound chip appears and tapping plays + sets the volume.
- Post wall: post_card.html renders a music bar (64px thumbnail,
  🎵 title — artist, ▶/⏸). The first tap lazily creates the player in
  a visible 16:9 area in the card (height capped at 200px) and plays
  from music_start; only one post plays at a time (starting another
  destroys the previous player). Unplayed posts load no iframes.
  A bare YouTube link pasted in post TEXT still auto-embeds as before
  — that behavior is separate and unchanged.
- User audio POSTS (kind='audio' MP3 uploads) are a post type and are
  untouched by all of the above.

## Games pack (Build F): My Views contest, post polls, story polls + AMA, live polls + trivia

New tables (all created in init_db, safe on existing DBs):
- polls(post_id PRIMARY KEY) — one row marks a post as carrying a poll; the post's body is the question.
- poll_options(id, post_id, idx, text) — 2–4 options per poll, idx = display order; text trimmed, ≤60 chars.

- live_poll_votes(poll_id, user_id, choice TEXT 'a'|'b', PRIMARY KEY(poll_id, user_id)) — one row per voter; changeable while the poll is active.

## Password recovery (Build O)

Ken's design (2026-10-24): the support/recovery mailbox is wearehereyouarehere@gmail.com and Milli runs recovery for users personally — this build is the machinery under that. There is NO free-form AI anywhere in the flow: the pages carry one fixed, scripted helper, and every decision is deterministic code.

The security core (never weaken):
- A reset link is only EVER sent to the email address already on the account. There is no alternate-address path for anyone — not for users, not for the owner, not for support. The owner hand-send rule says the same thing in the panel copy: the link goes to the account address, never to an address someone merely claims is theirs.
- POST /forgot renders the IDENTICAL success page in every outcome — account found, not found, emailed, queued, rate-limited (byte-identical response bodies; the tests assert this). Email lookup is case-insensitive, matching signup/login normalization (strip + lower).
- Tokens: secrets.token_urlsafe(32) (32 random bytes). Only sha256(token) is stored as the credential (password_resets.token_hash, UNIQUE). A token is usable iff a row matches the hash AND used_at IS NULL AND expires_at > now (lazy expiry on read — no sweeper).
- Single-use, enforced atomically: POST /reset claims the token with ONE guarded UPDATE (… SET used_at WHERE id AND used_at IS NULL, rowcount checked) in the same transaction that replaces users.pw_hash and DELETES every sessions row for the user — a completed reset signs the account out everywhere, and a double-submit/race can never set two passwords. Form refusals (empty password, mismatched confirm) do NOT consume the token. Password strength = signup's rule (non-empty) + the confirm match.
- One live token per account: minting a new one stamps used_at on all of the account's older unused rows (and wipes their token_plain) in the same request.
- Rate limits (counted on password_resets rows in the trailing hour): max 3 per account, max 10 per requester IP. Excess requests create nothing and still get the identical success page. Recovery is NOT gated on social state: private profiles and blocked-both-ways accounts reset exactly like anyone else (asserted in tests).

Delivery states (password_resets.delivery):
- 'emailed' — SMTP was configured and the send succeeded; sent_at stamped; token_plain was never kept past the send.
- 'queued' — SMTP is not configured (today's live state) OR a configured send failed. The row waits in the owner queue; a send failure never 500s /forgot.
- 'hand_sent' — the owner took the link from the queue, emailed it to the account address themselves, and marked it; sent_at stamped. Marking hand-sent wipes token_plain — the link keeps working regardless, because validation is by hash.

SMTP (stdlib smtplib only, STARTTLS, 10s timeout): env HERE_SMTP_USER + HERE_SMTP_PASS (both required — a Gmail APP password for wearehereyouarehere@gmail.com, never the account's real password), HERE_SMTP_HOST (default smtp.gmail.com), HERE_SMTP_PORT (default 587). From = HERE_SMTP_USER; To = the account address ONLY; subject "HERE — reset your password"; plain-text + simple-HTML bodies carry the {base}/reset/{token} link, the 1-hour note, and "If you didn't ask for this, ignore this email — your password won't change." GO-LIVE STEP (Ken/Milli, one-time, still outstanding): create the Gmail app password for wearehereyouarehere@gmail.com and set the four HERE_SMTP_* env vars on the Render "here" service. Until then every reset queues for hand-send — by design, not a bug.

Owner queue: the owner dashboard gains a "🔐 Password help" section (queued first, then recent; last 50) + a "Password help waiting" stat card (queued + unused + unexpired count). Row: user name, account email, asked time, link-dies time, derived state (used / expired / queued — needs hand-send / hand-sent / emailed), and for actionable rows (queued + unused + unexpired + token_plain present) two POST actions:
- POST /owner/pwreset/{id}/link {owner session} → owner/pwreset_link.html showing the FULL reset URL ({base}/reset/{token_plain}) with the account-address-only warning. Every other state (or a non-owner caller) → 303 /owner (or the owner-login bounce from require_owner). There is deliberately NO GET that reveals a link — reveals are POST-only, owner-session-only.
- POST /owner/pwreset/{id}/hand-sent {owner session} → delivery='hand_sent', sent_at=now, token_plain=NULL (guarded on delivery='queued' AND used_at IS NULL) → 303 /owner.

THE token_plain TRADEOFF (deliberate, Ken's queue design): a queued reset's raw token is stored in plaintext in password_resets.token_plain so the owner panel can show Milli the link to hand-send. This is a conscious exception to "hash-only" storage, bounded four ways: (1) it exists ONLY while delivery='queued' — emailed rows never keep it, and it is NULLed on email success, hand-sent, use, and supersede; (2) it is revealable only through an owner-session POST; (3) the credential check never uses it (validation is always the hash), so wiping it never breaks a sent link; (4) queued rows die on their own 1-hour expiry, after which the stored copy is worthless. The alternative (no stored copy) would make the hand-send queue impossible — the link has to exist somewhere for a human to send it. If SMTP goes live and stays healthy, the queue — and this column's exposure — empties in practice.

Guided helper (deterministic script, shown on GET /forgot and on the success page as a "Need help?" expandable): (1) check the email you typed is the one on your account; (2) check spam/promotions for an email from wearehereyouarehere@gmail.com; (3) links expire in 1 hour — ask for a fresh one if yours died; (4) still stuck? email wearehereyouarehere@gmail.com FROM the address on your account and a human (Milli) will walk you through it. The /forgot form itself spells out the three steps (type the account email → link goes to that email only → tap within 1 hour).

Admin visibility: password_resets rows ARE the audit trail, surfaced via the owner queue above. Resets deliberately write NOTHING to moderation_flags and NOTHING to notifications — the hourly flag-watch and the daily bughunt must never trip on recovery traffic, and no user gets any in-app notification about a reset (the email itself is the only message).

## Media storage: Cloudflare R2 (Build U)

Story-clip snapshots (`_story_clip_for_replies`) use a server-side CopyObject when the source is in R2, disk copy otherwise. **Failure honesty:** an R2 failure during save raises the generic friendly upload error (Build V's number-free string) — NEVER a 500 and NEVER a silent disk fallback (mixed storage would strand files).
- **Read path (no template changes):** every surface still renders `/uploads/<key>`. Disk mode: the historical StaticFiles mount. R2 mode: the mount is replaced by `GET /uploads/{key:path}` — traversal segments 404; a disk file wins (legacy pre-migration media serves exactly as before); else a cached (120 s, hits AND misses) R2 existence check → **302** to `R2_PUBLIC_BASE/<key>` when configured, else to a presigned GET (1 h). `avatar_url()` in R2 mode returns the URL without a local existence probe (a HEAD per avatar render is too slow; a ref to a truly deleted file shows a broken img instead of the letter placeholder — accepted tradeoff).
- **Direct upload for big video:** `POST /api/uploads/presign` {login required; JSON `{surface, filename, content_type}`} — surfaces `post`→posts/, `story`→stories/; video content types only (`video/mp4|webm|quicktime`). The SERVER mints the key: `<subdir>/u<user_id>-<uuid>.<ext>`. Response `{ok, direct:true, key, url}` with a SigV4 query-signed PUT URL (30 min, host-only signing, single PUT = up to 5 GB — no multipart). Disk mode, non-video, or a signing failure → `{ok:true, direct:false}` and the client behaves exactly as before. Client: `static/r2upload.js` (progressive enhancement on `input[type=file][data-r2up]` in home/page/daily/views composers + story creator) — XHR PUT with % progress, then submits the EXISTING form with a hidden `media_key` field and the file input cleared. `create_post_from_form` / story create accept `media_key` INSTEAD of a file (R2 mode only): `_accept_media_key` requires the key to fullmatch this user's minted pattern for that surface, the extension to be allowed on the surface, and a live HEAD proving the object exists — foreign keys, wrong types, traversal shapes, and never-uploaded keys all reject with a friendly error and create nothing.
- **Cap policy per mode:** DISK mode — unchanged (25 MB general / stories / market, 200 MB post video, 5 MB backgrounds, enforced inside save_upload). R2 mode — post video and story media caps are REMOVED (relayed and direct alike); image surfaces keep their historical caps as silent internal sanity limits (error copy stays the generic number-free string). Content-type/extension validation applies in BOTH modes, always.
- **Bucket CORS (ops step, REQUIRED before direct uploads work in a browser):** on the R2 bucket, allow origin `https://here-19yl.onrender.com` (ADD the custom domain `https://joincomehere.com` + `https://www.joincomehere.com` once DNS is wired), methods `PUT, GET, HEAD`, allowed headers `*`, expose `ETag`, max-age 3600. Without it the presigned PUT fails in-browser and the JS silently falls back to a relayed submit (which still works, capped only by policy above).
- **Migration runbook:** `scripts/migrate_uploads_to_r2.py` — DRY-RUN by default (prints would-copy/skip, writes nothing); `--apply` copies every file under HERE_UPLOADS to R2 under its identical key, verifying sizes via HEAD after each PUT. Idempotent: keys already in R2 with a matching size are skipped; size mismatches re-copy. Safe to run before, during, or after the env flip: reads resolve from either home at all times. Order of operations for go-live: create bucket + API token → set the 4 env vars (+ R2_PUBLIC_BASE when the public/custom domain is bound) on the Render "here" service → add the bucket CORS rule → deploy → run the migration with `--apply` → optionally clear /data/uploads media (keep the directory).
- **Tests:** tests/test_storage_r2.py (52 checks, fake S3 wire via monkeypatched storage._http_request): presign shape/auth/scoping/gating, post+story key flow (happy/foreign/missing/wrong-type/traversal), read-route 302/disk-fallback/404/presigned-GET fallback, per-mode caps via zero-streams, migration dry-run/apply/idempotent. Disk-mode behavior of every pre-existing suite is untouched (no existing test modified).
